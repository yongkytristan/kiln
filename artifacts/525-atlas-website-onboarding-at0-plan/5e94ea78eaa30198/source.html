1. Prinsip dasar

  • App baru dibuat di langkah terakhir. Link, Cek, Impor dan Review terjadi sebelum app ada, sama seperti onboarding sekarang. App tetap hanya dibuat oleh confirm yang sudah ada.
  • Arcane tidak butuh antrean atau background job sendiri. Atlas sudah menyimpan pekerjaannya dengan aman: kalau Arcane restart atau browser ditutup, pekerjaan di Atlas tetap jalan, dan Arcane cukup menanyakan statusnya lagi.
  • Hasil Atlas masuk sebagai usulan. Isian manual user di Review selalu menang.

5. Keamanan dan ketahanan

context_id

Atlas mengelompokkan semua pekerjaan per context_id. Usulannya: nilai dihitung dari HMAC(rahasia server, user + attempt).

  • Tidak bisa ditebak dan tidak memuat ID atau email user (syarat kontrak Atlas).
  • Selalu sama untuk user dan attempt yang sama: kepemilikan dicek dengan menghitung ulang, tanpa tabel baru.
  • User lain yang mencoba membaca ID pekerjaan orang lain mendapat "tidak ditemukan" dari Atlas.

Retry, reload, kedaluwarsa

  • Retry aman: submission_id dibuat di browser dan disimpan di draft sebelum dikirim. Respons hilang → kirim ID yang sama → Atlas mengembalikan pekerjaan yang sama (berlaku 24 jam).
  • Reload atau tutup tab: draft menyimpan URL, ID cek, ID impor dan pilihan halaman; saat dibuka lagi, polling dilanjutkan.
  • Kedaluwarsa: hasil cek bisa diimpor 30 menit setelah selesai (lewat itu, Arcane cek ulang diam-diam); draft berlaku 24 jam; hasil Atlas disimpan 30 hari.
  • Kapasitas Atlas penuh: kirim ulang ID yang sama setelah jeda yang disarankan Atlas.

6. Saat app dibuat

Saat confirm, Arcane membaca hasil Atlas sekali lagi, lalu menyimpan di app:

  • sumber impornya disimpan sebagai objek website_import di apps.requirements (D2, tanpa migrasi): URL, ID impor, attestation, halaman terpilih, waktu capture;
  • data yang dibutuhkan build pertama, disalin ke apps.requirements.

context_id tidak perlu disimpan: bisa dihitung ulang dari user dan attempt ID yang dipegang klien (HMAC). Attempt yang belum punya app tidak punya record di server (get_attempt menjawab 404), jadi tidak bergantung pada onboarding_attempt_id di app. Setelah app ada, ID itu juga tercatat di app.

9. Feature flag

Satu flag khusus UI untuk website dan marketplace (usulan, belum dikonfirmasi), usulan nama onboarding_link_import. Flag mati: chip dan tombol "Mulai dari link" disembunyikan, tapi impor yang sudah berjalan tetap bisa dilanjutkan. Route backend tidak dikunci flag; kalau Atlas belum dikonfigurasi, route menjawab 503.

10. Cara membuktikannya

  • Unit test client: semua kode error di kontrak Atlas, timeout, respons rusak, memakai server tiruan.
  • Unit test pemetaan: memakai hasil capture Atlas yang sudah tersimpan di repo (fixture).
  • Test service: user lain ditolak, respons hilang memakai ID yang sama, cek kedaluwarsa diulang otomatis, kapasitas penuh, hasil kedaluwarsa.
  • Test web: reload melanjutkan proses, flag hidup/mati, semua layar error.
  • Staging (AT-2): journey nyata dengan situs milik sendiri dan situs referensi, plus kasus ditolak, tidak ditemukan, robots, kapasitas, kedaluwarsa; screenshot di issue.

12. RFC #549: katalog marketplace sebelum app ada

Kasus penggunaan

Merchant yang jual di Tokopedia atau Shopee menempelkan link toko. Atlas membaca katalog, merchant meninjau, dan Arcane membangun toko dari produk yang dipilih lalu memandu merchant masuk program FDE. Kriteria penerimaan di #549: merchant masuk program FDE.

Masalah

Di antara Impor dan konfirmasi, Arcane harus menyimpan katalog yang dikembalikan Atlas (sampai 2.000 produk hari ini, batas baca Atlas sendiri), dengan sampai 15 gambar per produk sesuai kesepakatan di #549, dan katalog itu harus bertahan saat reload, tab ditutup, atau respons hilang. Belum ada app, jadi penyimpanan yang terikat app (apps.requirements) belum tersedia. Draft browser hanya ada di satu browser dan kedaluwarsa 24 jam. Kapasitasnya untuk data ini belum terverifikasi [INFERENCE]. Desain sekarang belum punya tempat untuk baris produk sebelum app ada.

Kondisi sekarang

  • Attempt dan draft ada di localStorage browser, dengan kunci dewabuilder.onboarding.draft.<attempt_id> (main di 3c01f7d2). Server tidak punya catatan untuk attempt tanpa app.
  • Gambar disalin ke aset milik user sebelum Review, tanpa stub app. Jonathan setuju pada 6 November. Aset hidup lebih lama dari app asalnya (ADR-067).
  • Produk: Jonathan memilih file data app yang dihasilkan untuk rilis pertama, tanpa database produk. Setiap produk yang dipilih disimpan, meskipun generasi hanya menerima sampel terbatas.
  • context_id Atlas tidak terikat app dan stabil (disepakati 6 November).
  • Belum dispesifikasikan: pemetaan dan penyimpanan milik Arcane untuk konteks pra-app, termasuk reload dan resume; tempat katalog lengkap pra-app disimpan; bagaimana pilihan menjadi file data app yang dihasilkan.
  • Import worker Dewastore menyimpan produk di database sendiri. Ini referensi perilaku, bukan skema untuk disalin. Dewastore sedang dipensiunkan.

Keputusan

Jonathan (10 November 2026): RFC tidak dibuka dulu. Tidak ada opsi yang dipilih; opsi di atas tetap tercatat sebagai bahan kalau pertanyaan ini dibuka lagi di #549. Bukti yang sudah ada: opsi B menambah tabel, artinya migrasi database, dan aturan eskalasi repo meminta keputusan manusia sebelum migrasi. Opsi A belum diukur untuk katalog Atlas penuh lintas perangkat. Pembersihan opsi C belum terverifikasi.

Pertanyaan kalau RFC dibuka nanti

  1. Di mana katalog pra-app disimpan, dan untuk berapa lama?
  2. Siapa pemiliknya, dan bagaimana aksesnya dibatasi (user dan attempt)?
  3. Bagaimana reload dan retry saat respons hilang dilanjutkan?
  4. Bagaimana pilihan final menjadi file data app yang dihasilkan saat konfirmasi?
  5. Apakah website (D1 opsi b) memakai catatan yang sama?

Yang menunggu dan yang jalan

Website memakai D1 opsi (a); opsi (b) tidak dikejar. Client Atlas, layar, dan alur website jalan tanpa menunggu RFC. Retensi katalog marketplace (MI-2) tetap pertanyaan terbuka di #549.

13. Kapan perlu RFC

Aturan dari Jonathan di #525 ("Guidance for Yongky and the assisting agent"):

  1. Mulai dari rencana implementasi singkat (halaman ini).
  2. Penempatan modul yang mengikuti arsitektur Arcane yang ada tidak perlu RFC.
  3. Keputusan struktural yang diperdebatkan, lintas area, atau sulit dibalik — misalnya siklus impor permanen baru, perubahan kepemilikan onboarding, atau penyimpanan katalog bersama sebelum app ada — diangkat sebagai pertanyaan dengan usulan RFC yang fokus. Arsitektur baru tidak dipilih diam-diam.
  4. Bagian yang terdampak menunggu keputusan; pekerjaan lain boleh jalan.
  5. RFC itu bersyarat, bukan kewajiban.
